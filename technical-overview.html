This document describes the current architecture of the ENRG protocol, including smart contracts, CPI integration, device lifecycle, and security model.

1. Architecture Overview

The ENRG protocol operates on a modular, multi-program architecture on Solana using Anchor Framework 1.0.3:

IoT Devices (ESP32 + PZEM-004T)
    ↓ Ed25519-signed proofs
Oracles (Switchboard / MVP)
    ↓ Verified data
enrg-mvp (Core Protocol)
    ↓ CPI calls
enrg-profile (Energy Profile)
    ↓
Energy Vault ↔ Staking ↔ Buyback & Burn
  • enrg-mvp: Core protocol — handles minting, staking, vault, device lifecycle, oracle registry, and buyback/burn.
  • enrg-profile: Energy Profile program — manages producer profiles with rated power, device type, location, and 30-day rolling energy window.
  • Oracle: Express.js server that validates IoT proofs and submits them on-chain.

2.3 CPI Integration

enrg-mvp calls enrg-profile via declare_program! (Anchor 1.0.3 CPI macro):

// In mint_energy:
crate::enrg_profile::cpi::record_production(
    CpiContext::new(
        ctx.accounts.profile_program.to_account_info(),
        crate::enrg_profile::cpi::accounts::RecordProduction {
            profile: ctx.accounts.profile.to_account_info(),
            authority: ctx.accounts.authority.to_account_info(),
        },
    ),
    energy_wh,    // u64
    timestamp,    // i64
    nonce,        // u64
)?;

The max_energy check in mint_energy reads profile.rated_power to enforce per-interval limits.

3. Device Lifecycle (ADR-0005)

Devices follow a strict state machine with 8 states. Each state has clearly defined transition rules:

UNREGISTERED
    │
    ▼
REGISTERED → (crypto identity created)
    │
    ▼
CLAIMED → (bound to owner)
    │
    ▼
PROVISIONED → (configured & synced)
    │
    ▼
ACTIVE → (producing & minting)
    │
    ├── (suspicious activity) → QUARANTINE → ACTIVE (released) or REVOKED
    │
    ├── (maintenance) → MAINTENANCE → ACTIVE
    │
    └── (end of life) → REVOKED
StateDescriptionValid Transitions
UNREGISTEREDDevice unknown to the system→ Registered
REGISTEREDDevice identity recorded on-chain→ Claimed
CLAIMEDOwner claims the device→ Provisioned
PROVISIONEDWi-Fi configured, time synced, config received→ Active
ACTIVEDevice producing and minting→ Quarantine, Maintenance, Revoked
QUARANTINESuspicious activity — proofs not minted→ Active (released), Revoked
MAINTENANCEService mode — proofs not sent→ Active
REVOKEDPermanently removed— (terminal)

Full specification: ADR-0005: Device States

4. Proof-of-Production (PoP)

Every 10 minutes, the IoT controller sends a signed proof containing:

OracleReport {
    device_id:    [u8; 32],
    timestamp:    i64,
    energy_wh:    u64,
    nonce:        u64,
    signature:    [u8; 64],
}

The smart contract verifies:

  • Ed25519 signature via sysvar instructions (solana_instructions_sysvar::get_instruction_relative)
  • Timestamp within 15 minutes of Solana block time
  • Nonce monotonically increasing (replay protection)
  • Energy limit based on device's rated_power from EnergyProfile

After verification, SRC is minted with a 15% protocol fee split:

  • 85% to producer
  • 15% fee → 20% Buyback & Burn, 40% Staking, 30% DAO, 10% Emergency

5.2 Replay Protection

Each proof includes a monotonically increasing nonce, validated by the smart contract. Old proofs are rejected.

5.3 Timestamp Validation

MAX_PROOF_AGE is set to 1 hour (3600 seconds). Proofs older than this are rejected.

5.4 Device State Machine

Only devices in Active state can mint energy. Quarantined or Revoked devices are blocked.

8. Architecture Decision Records (ADR)

The following ADRs document key architectural decisions. Click each to view the full document:

  • ADR-0001: Key Never Leaves Device — Ed25519 keys are generated and stored on the IoT device in ATECC608 Secure Element.
  • ADR-0002: Device Registry as Source of Truth — All device state is stored on-chain.
  • ADR-0003: Oracle Policy Engine — Oracle validates proofs before on-chain submission.
  • ADR-0004: Device Manifest — Each device has an on-chain manifest with metadata.
  • ADR-0005: Device States — Formal state machine for device lifecycle (8 states).
  • ADR-0006: Core Protocol vs Energy Profile — Separation of concerns between enrg-mvp and enrg-profile.
  • ADR-0007: Security Key Management — Hardware-grade key storage with ATECC608.
  • ADR-0008: OTA Secure Firmware Updates — Signed firmware updates for IoT devices.
  • ADR-0009: Governance Protocol — Progressive decentralization path to DAO.

Full ADR directory: docs/architecture/adr/

9. IoT Hardware Prototype

  • ESP32 DevKit V1 + PZEM-004T: Measures voltage, current, power, and energy.
  • Ed25519 on-device signing: Each measurement batch signed locally.
  • Wi-Fi submission every 10 minutes: Periodic pushes to the ENRG oracle.
  • OLED display: Local monitoring of live readings.
  • ATECC608 (planned): Hardware Secure Element for production deployments.
